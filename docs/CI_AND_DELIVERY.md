# Local verification and delivery

The owner selected local builds and E2E to preserve the GitHub Actions quota. The repository workflow was removed by request; no hosted workflow runs on pushes or pull requests. Hosted CI and artifact upload results are not claimed. A later workflow can be added when the owner chooses.

Run the PowerShell 7 script from any directory:

```powershell
& 'F:\kannan\projects\tokito ecosystem\tokito_cli\scripts\verify-local.ps1' -CargoPath 'C:\Users\PC\.cargo\bin\cargo.exe'
```

The script uses cached offline dependencies and creates a fresh isolated build directory under target/local-verification/<run-id>, preserving earlier outputs and avoiding replacement of potentially locked Windows executables. Use absolute alternate paths such as -TargetBase F:\TokitoCliBuilds and -DeliveryBase F:\TokitoCliDelivery when desired. TargetBase relocates Cargo build output plus geometry and optional dataset E2E receipts; the release binary and outer verification receipt stay under target/delivery/local unless DeliveryBase is supplied. External paths and existing parents are rejected if they contain reparse points. The portable runner has nineteen gates: formatting, locked offline Rust tests, warnings-denied Clippy, release build, board/geometry/GLB/model-resolution E2Es, historical v0.1 compatibility, BOM and model-assignment E2Es, candidate-envelope E2E, real CLI acceptance, and isolated STEP-probe gates. To include the pinned dataset component journey, pass both `-DatasetRepo` and `-DatasetBomReport`; that adds a twentieth gate. The dataset E2E checks the pinned MCXN236 commit and PCB hash, the available BOM report's U11 join, candidate envelope dimensions, assignment evidence, and the fail-closed shell-only result. The BOM source digest is a carried report claim because the raw BOM source is not materialized in this local checkout. The test does not prove that missing stackup is the only cause of the exporter's combined `missing_stackup_or_outline` condition. To audit the current NXP asset referenced by dataset PR #6, pass all of `-DatasetTwinGlb`, `-DatasetTwinComponentMap`, `-DatasetTwinManifest`, and `-DatasetTwinProvenance`; this adds another gate. It validates the pinned bytes, manifest, map, unique `ref:` selectors, and independently non-shared GLB component meshes. It does not certify package accuracy, board/photo registration, or a production footprint/PCB identity crosswalk. Neither profile drives a GUI, CAD viewer, or phone. The GLB journey checks container and mesh bounds/area/winding/closed edges, explicit partial consent, coverage, package input, determinism, no-overwrite and invalid-outline refusal. The real-model journey checks explicit roots, six UNO asset hashes, local WRL geometry/material inventory, units/bounds, byte budgets and malformed paths. Inputs and tested binary are fingerprinted; generated Python bytecode and __pycache__ paths are deliberately excluded from the source fingerprint. A receipt is written only if every selected gate passes.

Each verification.json records the local Windows architecture, actual Rust/Cargo/Python versions, passed checks, source-input SHA-256 values, and tested binary hash/size. The newest timestamped receipt under the selected delivery base is the current result; with the default, this is target/delivery/local/. Earlier receipts are historical.

The isolated STEP-evaluation crate adds three gates: formatting, locked offline tests and warnings-denied Clippy. BOM subprocess E2E and the analytic torus-inverse regression add two gates; model-assignment, Component Forge and twin-selector fixture E2Es add three more. The portable verifier therefore runs nineteen gates. The optional pinned MCXN236 U11 dataset case adds one, and the optional dataset PR #6 twin audit adds another, for up to twenty-one gates. Assignment tests inspect selectable body meshes, front/back coordinates, manifest provenance, population exclusions and hash refusal. BOM tests exercise exact identity joins, malformed and quoted CSV, UTF-8 BOM encoding and resource caps; they do not qualify 3D component geometry. Earlier ten- and thirteen-gate receipts cover only their original input snapshots and do not qualify this experiment or enable production STEP import.
The full suite verifies the board-shell GLB, bounded model capture, flat-triangle WRL profile, pure-Rust point/mesh placement helpers, strict source-stackup derivation, one- and two-component assembly GLBs, exact-refdes selector behavior, unsupported-side diagnostics, and coverage truncation on Windows. The tests model the App's documented name filter but do not run the App importer or Android renderer/selection. The suite does not prove Linux/MSRV, hosted CI, general WRL/STEP, complete KiCad conformance, manufacturing validity, Desktop/MCP integration or AR. Placement and stackup tests are source-derived checks, not a KiCad-generated export comparison. Hashes establish integrity, not publisher identity. A verification receipt is authoritative only when its recorded source fingerprints match the final implementation/scripts/tests; narrative documentation can be updated afterward, but must not be represented as an input to that earlier receipt.

No hosted workflow runs on pushes or pull requests. The CLI-specific roadmap is linked from the repository's Projects tab at https://github.com/TokitoAI/tokito-cli/projects; the organization-wide ecosystem project remains separate and unchanged. Hosted CI, release, and binary upload are out of scope.

The former repository's PR #9, CI logs, issues, branches, and Git bundle remain under target/recovery/github-before-recreation-20261009T150910Z. They are historical recovery records, not live checks or pull requests on the recreated repository.

When the optional dataset profile runs, its component E2E receipt binds the supplied BOM-report bytes by SHA-256. The outer `verification.json` records the dataset receipt's path and hash together with dataset commit, board hash, and BOM report hash. The receipt path is repository-relative when output is inside the checkout, and absolute for an external `-TargetBase`.

If the checkout volume cannot hold the delivered release executable and receipt, pass an absolute `-DeliveryBase` such as `F:\TokitoCliDelivery`. The script creates a fresh run directory there and rejects reparse-point parents. This moves only the local delivery copy and receipt; the project checkout and its existing evidence are preserved.
